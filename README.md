# Roosterly Support Ticket Agent

A safe, explainable, production-ready support agent for Roosterly (Dutch shift-planning SaaS), designed to answer customer inquiries covered by the help centre (`faq.md`) and escalate all other cases to a human support agent with an actionable English summary in under 60 seconds.

---

## How to run

```bash
# 1. Clone repository and set up virtual environment
git clone https://github.com/DatBoi07/Nordavo.git
cd Nordavo
python -m venv .venv
source .venv/bin/activate  # On Windows: .venv\Scripts\activate

# 2. Install package and dependencies
pip install -e .

# 3. Configure environment variables
cp .env.example .env
# Edit .env with your HELPDESK_API_KEY, HELPDESK_EMAIL, and GEMINI_API_KEY

# 4. Run unit tests (34 offline unit tests, ~0.8s)
pytest -v

# 5. Run evaluation suite (official 10 examples + 10 synthetic test cases)
python -m agent eval

# 6. Run agent in dry-run mode (safely processes tickets without POSTing)
python -m agent run --dry-run

# 7. Check status of API and local SQLite state
python -m agent status

# 8. Interactive debug trace on any single ticket
python -m agent debug T001

# 9. Final scored run (resets practice tickets and executes live handling)
python -m agent reset-and-run
```

## Decisions

1. **Safety Lives in Code, Not Prompts:** The LLM acts purely as an extractor of structured signals and metadata. Deterministic code (`policy.py`) enforces business rules, priorities, and action boundaries. Customer text is strictly treated as untrusted data inside `<ticket_data>` tags to neutralize prompt injection attempts (e.g., ticket T030).
2. **Direct Dutch Processing with English Auditability:** Customer tickets are processed directly in Dutch (preserving exact menu nomenclature such as `Team → Medewerker toevoegen`) while generating an English audit trail for non-Dutch reviewers (`summary_en`, `suggested_next_step_en`, and an independent back-translation `reply_en` generated by a secondary verifier model). Every run generates `reports/review.md` allowing full verification without speaking Dutch.
3. **Fail Toward a Human (Unsure = Escalation):** Whenever uncertainty arises—confidence below threshold (`0.75`), verifier score below `0.75`, disagreement between regex safety net and LLM, or missing FAQ coverage—the ticket is routed to human support (`handoff`).
4. **Assumptions Adopted:**
   - *Mixed questions* (FAQ how-to + refund request): Escalate to human so both are handled safely.
   - *Bug reports & Outages:* App malfunctions or blocking bugs escalate to human (P1 for platform-wide outages, P2 for single-customer blockers); only pure questions asking where to check maintenance receive the status page link (F11).
   - *Customer Plan Awareness:* Customer plan (`customer_plan`) is referenced during drafting; Basis customers asking for Plus integrations (Nmbrs, Loket.nl, AFAS) are informed that an upgrade is required (F04, F05).
   - *Tone & Formality:* Mirrors the customer's register (informal *je/jij* by default, formal *u/uw* if addressed formally), signed off with `Team Roosterly Support`.
5. **AI Tooling Transparency:** Built with Google Antigravity and Gemini models (`gemini-2.5-flash` for extraction/drafting, `gemini-3.5-flash-lite` for verification). Every module was written to be explainable and maintainable in a live review session.

## Reliability

- **Transient Errors (503 & Network Drops):** Retried automatically with exponential backoff and jitter (0.5s base, up to 6 attempts).
- **Rate Limiting (429):** Client-side token bucket limiter restricts outbound requests to 4 req/s (safely below the 5 req/s server ceiling); HTTP 429 responses parse and respect `Retry-After`.
- **Duplicate Prevention (409):** HTTP 409 (`already_handled`) is treated as a terminal success state, immediately reconciled in the local database and never retried.
- **Crash Recovery & Idempotency:** SQLite database (`state/agent.db`) records state transitions (`pending` → `decided` → `sending` → `sent`). If interrupted, stored decisions are dispatched without redundant LLM calls; tickets marked `sending` are checked against `GET /tickets/{id}` prior to resending.
- **Data Privacy & PCI Compliance:** IBANs (mod-97 validated) and credit card numbers (Luhn validated) are redacted to `[REDACTED_IBAN]` and `[REDACTED_CARD]` *before* LLM processing, in logs, and in draft responses. Secrets remain isolated in `.env`.

## Eval and fix

### Evaluation Baseline vs. Post-Fix Performance

Evaluated against the 10 official gold examples from `GET /examples` and 10 synthetic edge cases (`evals/data/extra_cases.json`):

| Metric | Baseline (Official) | After Fix (Official) | Synthetic Extra Cases |
|---|---|---|---|
| **Action Accuracy** | **100.0%** (10/10) | **100.0%** (10/10) | **100.0%** (10/10) |
| **Priority Accuracy** | 60.0% (6/10) | **100.0%** (10/10) | 90.0% (9/10) |
| **Category Accuracy** | 100.0% (10/10) | 90.0% (9/10) | 100.0% (10/10) |
| **Language Accuracy** | 100.0% (10/10) | 100.0% (10/10) | 100.0% (10/10) |
| **Safety Violations (Unsafe Replies)** | **0** (0/10) | **0** (0/10) | **0** (0/10) |
| **Escalation Recall** | 100.0% | 100.0% | 100.0% |
| **Over-escalation Rate** | 0.0% | 0.0% | 0.0% |
| **Exact Match (All 4 Fields)** | 60.0% (6/10) | **90.0%** (9/10) | **90.0%** (9/10) |

- **The Problem Diagnosed:** In the baseline, standard how-to questions (E02, E04, E05) were assigned P3 instead of P4 because routine UI workflows were misclassified as "workarounds". Conversely, device requirement bugs (E01) were escalated to P2 because device crashes triggered an unconditional blocker floor.
- **The Systematic Fix:** (1) Introduced explicit `suggested_priority` in the classifier schema with rigid definitions; (2) added policy logic ensuring pure FAQ replies default to P4 (or P3 for device limitations), while customer-blocked bugs without workarounds enforce P2; (3) bumped prompt version to `v2`. Priority accuracy reached 100% on the official examples.

### Cost Calculation per 100 Tickets

Based on the 30-ticket dry run:
- **Input Tokens:** 65,161 tokens across 30 tickets (average 2,172 tokens/ticket)
- **Output Tokens:** 20,087 tokens across 30 tickets (average 670 tokens/ticket)
- **Pricing:** `$0.15` / 1M input tokens, `$0.60` / 1M output tokens (USD to EUR rate: `0.92`)
- **Arithmetic:**
  $$\text{Cost per ticket} = \left(\frac{2{,}172}{10^6} \times 0.15 + \frac{670}{10^6} \times 0.60\right) \times 0.92 = \$0.000728 \times 0.92 = €0.000670$$
  $$\text{Cost per 100 tickets} = 100 \times €0.000670 = \mathbf{€0.067}$$
The total cost to run all 30 practice tickets is under **€0.02**, well below the €1 budget ceiling.

## What I would improve

1. **Native Dutch Speaker Review:** While the dual-LLM back-translation and grounding checks verify facts and menu paths, subtle nuances in Dutch tone (e.g. regional variations between Dutch and Flemish idioms) would benefit from periodic native speaker spot-checks.
2. **Dual-Action Support in Helpdesk API:** Currently, the API forces a single decision (`reply`, `handoff`, or `close`). For tickets like suspected platform outages (e.g. T006), the optimal customer experience is a **combined action**: immediately send an automated acknowledgment with the status page link (`reply`) while concurrently dispatching an escalation ticket to on-call engineering (`handoff`).
3. **Calibrated Confidence Thresholding:** Replace a static `0.75` threshold with a conformal prediction calibration based on historical support ticket outcomes.
